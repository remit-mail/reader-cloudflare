# reader-cloudflare

remit reader on Cloudflare Workers. A TypeScript Worker in `src/`, configured by `wrangler.jsonc`, serving the React web client in `packages/web` as assets; OpenTofu in `infra/` for the Cloudflare account.

## Rules

- TypeScript only. No Python.
- npm workspaces with one lockfile at the root. Current major versions of every tool; Node 24 (`.nvmrc`).
- Biome formats and lints. Run `npm run fix` before every commit.
- Run `npm run ci` before every push.
- `main` is protected. Branch from `origin/main`, run `npm run ci` before pushing, and open a pull request with a conventional title under 72 characters and a four-line body. Arm `gh pr merge --squash --auto`; it squash merges once `ci` is green and deletes the branch.
- Never re-key or reshape rows on the request path or at Durable Object start; a schema change that reshapes rows means wipe the tenant object and resync, or a D1 migration in `npm run db:migrate`. A data migration reader ships for its own SQLite store is ported as a tenant mail migration.
- CI is one fast job named `ci`, the required check on `main`: `npm ci`, then `npm run ci`. It runs on every pull request and every push to `main`, and never deploys.
- The Worker logs one JSON object per line through `log` in `src/log.ts`. Workers Observability is on in `wrangler.jsonc`.
- `npm run commit` writes the gitignored `src/commit.ts` from `WORKERS_CI_COMMIT_SHA`, else `git rev-parse HEAD`. `npm run build` runs it first, and `wrangler.jsonc` uses `npm run build` as the build command, so `dev` and `deploy` ship fresh assets; `typecheck` runs it too. `GET /api/config` carries it as `buildCommit`, so a deploy matches a commit; the stale-build reload in `packages/web/src/stale-build.ts` compares it against the loaded bundle.

## What the code does not tell you

1. Reader's handlers, repositories, sync and send all run inside the `TenantMail` Durable Object, because a repository must sit next to its SQLite store. The Worker is the Access boundary and holds none of reader's logic. Its repositories and the D1 app store run on `CLOUDFLARE_SQLITE_LIMITS` in `src/api/config.ts`, 100 bound parameters per statement, the limit both Durable Object SQLite and D1 enforce.
2. Reader's `deriveAccountConfigId` derives the account config id from the Access subject. Every `threadId` and `addressId` embeds it, so changing it means wiping the mail object. A service token's JWT has an empty `sub`, so the Worker takes its `common_name`, the token's client id, as the subject; the agent token gets its own tenant and account config id, apart from every user. A wipe renames the Durable Object class across two deploys, because Cloudflare refuses a class delete and a rebind in one deploy.
3. Work runs on five queues by urgency (sync, body, mutation, smtp, fanout) plus one shared dead-letter queue. Bodies have their own queue at concurrency 1 so header syncs never wait behind them, and the sync queue runs at concurrency 2 so it cannot fan out into dozens of calls waiting on the one IMAP slot. `src/queue/routing.ts` picks the queue from reader's event type, and reader's port names play no part. `MAX_RETRIES` in that file must match each consumer's `max_retries` in `wrangler.jsonc`, so a handler gets `max_retries + 1` tries. `CONSUMER_SETTINGS` in `src/api/host-limits.ts` must match each consumer's `max_batch_size`, `max_batch_timeout` and `max_concurrency`, and `BODY_BATCH_SIZE` there sizes a body job, while `BODY_PROCESS_CONCURRENCY` and `BODY_PROCESS_BYTES_IN_FLIGHT` cap how many bodies, and how many bytes of them, one job holds in the isolate's 128 MB at once. `npm run check:retries` (part of `npm run ci`) fails when any of them differ. Every `max_batch_timeout` is 0: Cloudflare holds a lone event up to 5 s, and reader gives a queued move 5 s to settle before not spam fails. Mailbox create, rename and delete ride the unordered mutation queue here, not reader's per-account FIFO; that is safe because reader's `MailboxQueueService` records a rename or delete only from `synced` or `failed` (`INTENT_RECORDABLE_FROM` in `@remit/mailbox-service`) and answers 409 while the folder, or for a rename any folder under it, still has a create, rename or delete pending. Every consumer runs inside the tenant object over a one-slot IMAP pool, which is the account's single connection, and each delivery gets its own CPU budget, `limits.cpu_ms` in `wrangler.jsonc`, which must match `CPU_MS_PER_INVOCATION` in `src/api/host-limits.ts` (also checked by `check:retries`, which also fails when `env.e2e` binds different `ratelimits` names than the top level). The `*/5 * * * *` cron in `wrangler.jsonc` must match `TICK_INTERVAL_MS` in `src/mail/scheduler-tick.ts`, the dedup bucket of reader's `runSchedulerTick`; `scheduled()` ticks every tenant in `tenant_key` one Durable Object call at a time, and Cloudflare Queues ignore that dedup id, so a sync already queued is held off only by reader's due-check and mailbox lock.
4. When reader and Workers disagree, reader changes. Workers forbid runtime code generation. The `@remit/api-openapi-spec` package ships reader's request validators precompiled. The repo injects every socket as a transport (imapflow `transport`, nodemailer `getSocket`). Cloudflare's `cloudflare:sockets` refuses `rejectUnauthorized: false`. The subpaths the Worker imports (`@remit/backend/serve`, `@remit/backend/handlers`, each worker's `/process`) must stay free of AWS and Lambda code. Fix a break in a reader package in reader with a `fix` or `feat` commit; its merge to reader's `main` publishes it, then bump it here. Never patch `node_modules`.
5. Workers Builds deploys every push to `main`, with an empty build command and `npm run deploy` as the deploy command. It deploys the `dev` stage, runs `seed:dev` and `smoke:dev` against it, and deploys `prod` only when both pass, so a broken build never reaches prod. A prod fix ships through dev like any other change, and a broken dev stage is fixed forward with a pull request; there is no way to skip dev. Each stage runs `tofu apply` on its own state key, renders the git-ignored `wrangler.deploy.jsonc`, applies D1 migrations and then runs `wrangler deploy` on it, whose `build.command` builds. `npm-scripts/stages.mjs` holds what differs by configuration: one `mailSync` flag, off on dev, renders no cron and no consumer for the queues that reach a mail server (sync, body, mutation, smtp), so dev never syncs a mailbox and holds test data only. The committed `wrangler.jsonc` holds the portable settings, with synthetic bindings for `dev` and `e2e`. The render keeps those settings and swaps in the name, account, route, Access vars, D1, R2, queue and Secrets Store values from the Tofu outputs. The Worker routes a queue by the suffix after its last dash (`-sync`, `-body`, `-mutation`, `-smtp`, `-fanout`, `-dlq`). `src/api/storage.ts` keeps `reader-cloudflare-mail` as the storage URI label on every deployment, because stored rows embed it. Non-production branch builds are off, `npm run deploy` refuses any branch but `main`, and GitHub holds no Cloudflare token. Never deploy or apply from the dev machine. Local scripts read credentials from `~/.config/<project>/cf-env` and never print them. Build logs need a user-owned token; account tokens are refused by the Builds API, so `builds` reads `CLOUDFLARE_USER_TOKEN` from `cf-user-env`. The account runs on Workers Paid because the Free plan's daily Durable Object row-write cap failed API reads (issue #5). This repo is one of three planned composition roots over reader's packages, with AWS and Scaleway next, each on that cloud's native primitives.

6. `packages/login` is a second Worker, `<project>-login` on `login_hostname`: a better-auth OIDC identity provider that Access trusts, with its own D1 and no Access application in front. People join by invite only. `operator_emails` in the deploy config names who gets the server-rendered `/admin` page, which answers 404 to anyone else; every admin action takes a single-use step-up bound to operator, session, action and target, and no operator can act on another. It is the only identity provider of both Access applications, which send a visitor straight to it, with a 15 minute Access session that renews silently from the 90 day login session; each stage also holds the shared Zero Trust organization session at 15 minutes. With the one-time PIN gone, nobody gets past Access while the login Worker is broken; the only way back in is a pull request that adds the PIN back to `allowed_idps`. Deploy creates `LOGIN_AUTH_SECRET` (`DEV_` on dev) in the Secrets Store with the runner token and never reads it back, and upserts the one `oauth_client` row. Its invocation logs are off and it logs only allowlisted fields. It refuses any request that carries Access credentials. The `captureLoginMail` flag in `npm-scripts/stages.mjs`, on for dev only and refused for prod at render, renders the dev login Worker with `MAIL_CAPTURE` and no `send_email` binding, so it stores every message in its `captured_mail` table for an hour instead of sending it. The dev app Worker binds the login Worker's `CapturedMailReader` entrypoint, which has no HTTP route, and serves it on `GET /api/dev/login-mail` only to the dev agent service token; `npm run login:mail` reads invite links and reset codes there.

## Infra

The repo holds no deployment values. A deploy config names a deployment, and `npm-scripts/deploy-config.mjs` validates it: `account_id`, `zone_name`, `app_hostname`, `dev_app_hostname`, `alert_email`, `login_hostname`, `dev_login_hostname`, `email_sender`, `dev_email_sender` and `operator_emails`. Its one source is the project's entry in the private `mvhenten/cloudflare-builds-bootstrap` repo, which sets it as JSON in the `DEPLOY_CONFIG` Workers Builds variable on the `main` trigger. Secrets stay out of it: the `deploy.secrets.json` object in `<project>-builder-secrets`, written by `tofu-bootstrap --secrets`, holds an optional `msoauth` object with the Microsoft app's `client_id` and `client_secret`; without it Microsoft sign-in answers 501. `npm run deploy` parses `DEPLOY_CONFIG`, merges the secrets object, validates both, fails when any of its values appears in the repo, and passes each field to Tofu as a `TF_VAR_`. The project name is the `name` in `package.json`, or the Builds variable `DEPLOY_PROJECT` when set; it reaches Tofu as `var.project`, from which every resource name derives. `npm run check:no-config` keeps account ids, Access values and e-mail addresses out of git, plus every value of the deploy config, which it reads from `cloudflare-builds-bootstrap` through `gh api` like `infra:plan`; without access to that repo, as in CI, it says so in one line and scans without those values.

A new deployment needs a Cloudflare account on Workers Paid, the zone of `app_hostname` in that account, and a Zero Trust organization. The first operator gets an invite from the login Worker's hourly cron once it deploys. Export a privileged key as `CLOUDFLARE_BOOTSTRAP_TOKEN` and run `tofu-bootstrap <project> --debug-token-exists --secrets-store` from the dotfiles repo, adding `--secrets <file>` for a Microsoft app. Add the repo to `cloudflare-builds-bootstrap` as a Worker named `<project>`, with an empty build command, `npm run deploy` as the deploy command, branch `main`, and an `environment` holding the deploy config as `DEPLOY_CONFIG`, plus `DEPLOY_PROJECT` when `<project>` differs from the `package.json` name; its merge connects the repo and sets the variables. Connecting creates the Worker, and the `import` block in `infra/main.tf` adopts it on the first apply. Push to `main`.

`tofu-bootstrap` is the one human-run step, like `cdk bootstrap`. It creates the R2 state bucket `<project>-tfstate`, its S3 keys, the runner token `<project>-tofu` and, with `--secrets-store`, the Secrets Store `<project>`. It uploads a local state passed with `--state` and writes the runner token and the state keys into the private bucket `<project>-builder-secrets`. It stores every value in dotfiles behind the dotfiles key. Revoke the bootstrap key afterwards if it differs from the runner. After it no local secret is needed to change the account: an infra change is a pull request, and its merge makes Workers Builds run `tofu apply` against the R2 backend, on the OpenTofu version `npm-scripts/tofu.mjs` pins, downloads and checks. `npm run deploy` reads the builder objects through the R2 REST API with the token Builds injects. The builder bucket is readable only by that token and the runner, never the debug token. `npm run infra:plan` takes the runner token and state keys from the shell, the deploy config from `cloudflare-builds-bootstrap` on `main` through `gh api`, and the secrets object from the builder bucket. GitHub holds no Cloudflare token and CI never plans, applies or deploys. Before the first `tofu apply`, `npm-scripts/runner-grant.mjs` has the runner token add each permission group in `RUNNER_GROUPS` it lacks to its own policies, account groups on the account and zone groups on `zone_name` only, through its Account API Tokens Write, then checks it still holds that group, so widening the runner is a pull request too.

Tofu runs once per stage, as `var.stage`. Dev suffixes every name with `-dev`, takes `dev_app_hostname` and no Microsoft app, keeps its state in `<project>-dev.tfstate`, and stores its master key as `DEV_MASTER_KEY`. An account holds one Secrets Store, so `tofu-bootstrap` makes it and both stages look it up by name; the debug token and the usage alerts exist on prod only. Per stage, Tofu owns the D1 database, R2 bucket, queues, Secrets Store secret `MASTER_KEY` and, when configured, `MSOAUTH_CLIENT_SECRET`, the Worker shell and the Access application on `app_hostname`: the login Worker's identity provider for people, plus a Service Auth policy for the `<project>-agent` service token that agents call the API with. A second Access application, `<project>-public`, bypasses Access on the calendar feed path and the Microsoft OAuth callback only. Every Access application lists `allowed_idps` explicitly, and preconditions fail the plan when one allows the other stage's login IdP or names `login_hostname`. The custom domain attaches on the first deploy. Workers Builds runs `wrangler deploy` with the token it injects into the deploy step, and `tofu apply` with the runner token from the builder bucket.

Tofu mints the `debug` token in `infra/tokens.tf` from permission groups looked up by name: read-biased (Workers scripts, CI, queues and account settings read, with no D1 read and no tail, because both span the account and a tail carries cookies; observability write for saved queries; on every zone, analytics read plus firewall services, zone WAF and zone settings write; read on the state bucket), it lives in `cf-env`, which `wrangler`, `logs` and `dashboards` read, and they restore a missing `cf-env` with `dotfiles-key decrypt <project>-debug-token`. It is the one credential that cannot fetch itself, so dotfiles keeps it; with it agents do read-only work, and `cf-env:write` and `access-env:write` read the remote state with S3 keys derived from it (key id = token id, secret = sha256 of the value), then re-encrypt and push to dotfiles. Rotate a tofu-minted credential with a pull request that renames its resource, so the next apply mints the new one before it revokes the old, then run its `:write` script, with `TFSTATE_ACCESS_KEY_ID` and `TFSTATE_SECRET_ACCESS_KEY` in the shell when the old debug token is gone; rotate the runner token and state keys by running `tofu-bootstrap` again.

A user-owned read-only token for the Workers Builds API lives in `~/.config/<project>/cf-user-env` as `CLOUDFLARE_USER_TOKEN`; restore a missing one with `dotfiles-key decrypt cloudflare-user-readonly -o ~/.config/<project>/cf-user-env`.
