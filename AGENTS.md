# reader-cloudflare

remit reader on Cloudflare Workers. A TypeScript Worker in `src/`, configured by `wrangler.jsonc`, serving the React web client in `packages/web` as assets; OpenTofu in `infra/` for the Cloudflare account.

## Rules

- TypeScript only. No Python.
- npm workspaces with one lockfile at the root. Current major versions of every tool; Node 24 (`.nvmrc`).
- Biome formats and lints. Run `npm run fix` before every commit.
- Run `npm run ci` before every push.
- `main` is protected. Branch from `origin/main`, run `npm run ci` before pushing, and open a pull request with a conventional title under 72 characters and a four-line body. Arm `gh pr merge --squash --auto`; it squash merges once `ci` is green and deletes the branch.
- Never migrate or re-key existing data on the request path or at Durable Object start; a schema change that reshapes rows means wipe the tenant object and resync, or a D1 migration in `npm run db:migrate`.
- CI is one fast job named `ci`, the required check on `main`: `npm ci`, then `npm run ci`. It runs on every pull request and every push to `main`, and never deploys.
- The Worker logs one JSON object per line through `log` in `src/log.ts`. Workers Observability is on in `wrangler.jsonc`.
- `npm run commit` writes the gitignored `src/commit.ts` from `WORKERS_CI_COMMIT_SHA`, else `git rev-parse HEAD`. `npm run build` runs it first, and `wrangler.jsonc` uses `npm run build` as the build command, so `dev` and `deploy` ship fresh assets; `typecheck` runs it too. `GET /api/config` carries it as `buildCommit`, so a deploy matches a commit; the stale-build reload in `packages/web/src/stale-build.ts` compares it against the loaded bundle.

## What the code does not tell you

1. Reader's handlers, repositories, sync and send all run inside the `TenantMail` Durable Object, because a repository must sit next to its SQLite store. The Worker is the Access boundary and holds none of reader's logic. Its repositories and the D1 app store run on `CLOUDFLARE_SQLITE_LIMITS` in `src/api/config.ts`, 100 bound parameters per statement, the limit both Durable Object SQLite and D1 enforce.
2. Reader's `deriveAccountConfigId` derives the account config id from the Access subject. Every `threadId` and `addressId` embeds it, so changing it means wiping the mail object. A service token's JWT has an empty `sub`, so the Worker takes its `common_name`, the token's client id, as the subject; the agent token gets its own tenant and account config id, apart from every user. A wipe renames the Durable Object class across two deploys, because Cloudflare refuses a class delete and a rebind in one deploy.
3. Work runs on five queues by urgency (sync, body, mutation, smtp, fanout) plus one shared dead-letter queue. Bodies have their own queue at concurrency 1 so header syncs never wait behind them, and the sync queue runs at concurrency 2 so it cannot fan out into dozens of calls waiting on the one IMAP slot. `src/queue/routing.ts` picks the queue from reader's event type, and reader's port names play no part. `MAX_RETRIES` in that file must match each consumer's `max_retries` in `wrangler.jsonc`, so a handler gets `max_retries + 1` tries. `CONSUMER_SETTINGS` in `src/api/host-limits.ts` must match each consumer's `max_batch_size` and `max_concurrency`, and `BODY_BATCH_SIZE` there sizes a body job, while `BODY_PROCESS_CONCURRENCY` and `BODY_PROCESS_BYTES_IN_FLIGHT` cap how many bodies, and how many bytes of them, one job holds in the isolate's 128 MB at once. `npm run check:retries` (part of `npm run ci`) fails when any of them differ. Every consumer runs inside the tenant object over a one-slot IMAP pool, which is the account's single connection, and each delivery gets its own 30 s CPU budget. The `*/5 * * * *` cron in `wrangler.jsonc` must match `TICK_INTERVAL_MS` in `src/mail/scheduler-tick.ts`, the dedup bucket of reader's `runSchedulerTick`; `scheduled()` ticks every tenant in `tenant_key` one Durable Object call at a time, and Cloudflare Queues ignore that dedup id, so a sync already queued is held off only by reader's due-check and mailbox lock.
4. When reader and Workers disagree, reader changes. Workers forbid runtime code generation. The `@remit/api-openapi-spec` package ships reader's request validators precompiled. The repo injects every socket as a transport (imapflow `transport`, nodemailer `getSocket`). Cloudflare's `cloudflare:sockets` refuses `rejectUnauthorized: false`. The subpaths the Worker imports (`@remit/backend/serve`, `@remit/backend/handlers`, each worker's `/process`) must stay free of AWS and Lambda code. Fix a break in a reader package in reader, publish it with a `pkgs-v*` tag, then bump it here. Never patch `node_modules`.
5. Workers Builds deploys every push to `main`, with an empty build command and `npm run deploy` as the deploy command, which runs `tofu apply`, renders the git-ignored `wrangler.deploy.jsonc`, applies D1 migrations and then runs `wrangler deploy` on it, whose `build.command` builds. The committed `wrangler.jsonc` holds the portable settings, with synthetic bindings for `dev` and `e2e`. The render keeps those settings and swaps in the name, account, route, Access vars, D1, R2, queue and Secrets Store values from the Tofu outputs. The Worker routes a queue by the suffix after its last dash (`-sync`, `-body`, `-mutation`, `-smtp`, `-fanout`, `-dlq`). `src/api/storage.ts` keeps `reader-cloudflare-mail` as the storage URI label on every deployment, because stored rows embed it. Non-production branch builds are off, `npm run deploy` refuses any branch but `main`, and GitHub holds no Cloudflare token. Never deploy or apply from the dev machine. Local scripts read credentials from `~/.config/<project>/cf-env` and never print them. Build logs need a user-owned token; account tokens are refused by the Builds API, so `builds` reads `CLOUDFLARE_USER_TOKEN` from `cf-user-env`. The account runs on Workers Paid because the Free plan's daily Durable Object row-write cap failed API reads (issue #5). This repo is one of three planned composition roots over reader's packages, with AWS and Scaleway next, each on that cloud's native primitives.

## Infra

The repo holds no deployment values. One deploy config, `deploy.config.json`, names a deployment. `npm-scripts/deploy-config.mjs` validates it: `project`, `account_id`, `zone_name`, `app_hostname`, `owner_emails` and `alert_email`. It stays out of git. `tofu-bootstrap` encrypts it into dotfiles as `<project>-deploy-config` and writes it to the `<project>-builder-secrets` bucket. `npm run deploy` reads it there and passes each field to Tofu as a `TF_VAR_`. Every resource name derives from `var.project`. The project defaults to the `name` in `package.json`; a Builds variable `DEPLOY_PROJECT` overrides it. `npm run check:no-config` keeps account ids, Access values and e-mail addresses out of git, plus every value of a local deploy config.

A new deployment: clone the repo and write `deploy.config.json` with the six fields. Export a privileged key as `CLOUDFLARE_BOOTSTRAP_TOKEN` and run `tofu-bootstrap <project> --debug-token-exists --config deploy.config.json` from the dotfiles repo. Connect the repo to Workers Builds on the `<project>` Worker, with build command `npm run build` and deploy command `npm run deploy`, then push to `main`.

`tofu-bootstrap` is the one human-run step, like `cdk bootstrap`. It creates the R2 state bucket `<project>-tfstate`, its S3 keys and the runner token `<project>-tofu`. It uploads a local state passed with `--state` and writes the runner token, the state keys and the deploy config into the private bucket `<project>-builder-secrets`. It stores every value in dotfiles behind the dotfiles key. Revoke the bootstrap key afterwards if it differs from the runner. After it no local secret is needed to change the account: an infra change is a pull request, and its merge makes Workers Builds run `tofu apply` against the R2 backend, on the OpenTofu version `npm-scripts/tofu.mjs` pins, downloads and checks. `npm run deploy` reads the builder objects through the R2 REST API with the token Builds injects. The builder bucket is readable only by that token and the runner, never the debug token. `npm run infra:plan` takes the runner token and state keys from the shell and the deploy config from `~/.config/<project>/deploy.config.json`, restored from dotfiles. GitHub holds no Cloudflare token and CI never plans, applies or deploys.

Tofu owns the D1 database, R2 bucket, queues, Secrets Store with its `MASTER_KEY`, the Worker shell and the Access application on `app_hostname`: one-time PIN for `owner_emails`, plus a Service Auth policy for the `<project>-agent` service token that agents call the API with. The custom domain attaches on the first deploy. Workers Builds runs `wrangler deploy` with the token it injects into the deploy step, and `tofu apply` with the runner token from the builder bucket.

Tofu mints the `debug` token in `infra/tokens.tf` from permission groups looked up by name: read-biased (Workers scripts, tail, CI, D1, queues and account settings read; observability write for saved queries; on every zone, analytics read plus firewall services, zone WAF and zone settings write; read on the state bucket), it lives in `cf-env`, which `wrangler`, `tail`, `logs` and `dashboards` read, and they restore a missing `cf-env` with `dotfiles-key decrypt <project>-debug-token`. It is the one credential that cannot fetch itself, so dotfiles keeps it; with it agents do read-only work, and `cf-env:write` and `access-env:write` read the remote state with S3 keys derived from it (key id = token id, secret = sha256 of the value), then re-encrypt and push to dotfiles. Rotate a tofu-minted credential with a pull request that renames its resource, so the next apply mints the new one before it revokes the old, then run its `:write` script, with `TFSTATE_ACCESS_KEY_ID` and `TFSTATE_SECRET_ACCESS_KEY` in the shell when the old debug token is gone; rotate the runner token and state keys by running `tofu-bootstrap` again.

A user-owned read-only token for the Workers Builds API lives in `~/.config/<project>/cf-user-env` as `CLOUDFLARE_USER_TOKEN`; restore a missing one with `dotfiles-key decrypt cloudflare-user-readonly -o ~/.config/<project>/cf-user-env`.
